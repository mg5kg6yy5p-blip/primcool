# PrimeCool — CMMS/PM Spec vs. Existing System (Gap Analysis)

> **Phase 0 deliverable.** This maps the SAP-PM-flavored build spec onto what the
> repository **already implements**, instead of assuming a greenfield build.
> Status legend: **Present** (exists and broadly matches intent) · **Partial**
> (exists but missing a spec behavior) · **Missing** (no equivalent today).
>
> Generated by survey of `database.py` (schema), `main.py` (routes/roles), and
> the HTML SPAs. Date: 2026-06-18.

## Stack reality (governs every "how")

The spec names Postgres + SQLAlchemy 2.0 + Alembic + Pydantic v2 + React/Vite as
defaults **only if the repo hasn't already established a stack**. It has:

| Spec default | This repo actually uses |
|---|---|
| PostgreSQL | **SQLite** (WAL), ~13 MB live DB |
| SQLAlchemy ORM | **No ORM** — raw `sqlite3`, hand-written SQL in `database.py` |
| Alembic | **Idempotent additive migrations** inside `init_db()` |
| Pydantic v2 as source of truth | FastAPI's bundled pydantic, used lightly |
| React/Vite | **Vanilla-JS HTML SPAs** (`admin.html` ≈ 1 MB, no `package.json`) |

**Decision:** build in SQLite / raw-SQL / vanilla-JS. Postgres-specific spec items
(partial unique indexes, native PG enums, PG triggers, JSONB) are re-expressed in
SQLite terms: partial unique index → SQLite `CREATE UNIQUE INDEX ... WHERE`;
PG enum → `TEXT ... CHECK (... IN (...))`; JSONB → `TEXT` holding JSON; PG
RAISE-on-UPDATE trigger → SQLite `BEFORE UPDATE ... RAISE(ABORT,...)` (the
existing `audit_log` already uses this pattern via `_audit_guard`).

## Ranked gap list (what's actually missing, highest leverage first)

1. **Functional-location ↔ equipment temporal split** (FL slots + `equipment_install` with the two active-install partial-unique invariants, equipment `status`, `warranty_months`). *Unlocks: refurbish-and-swap, warranty, equipment timeline.* — **Missing**
2. **Billing-class layer + draft-invoice-from-confirmations** (`billing_class` on the order; resolve warranty/contract/billable/goodwill; aggregate visit confirmations into draft lines; GCT as one optional % line). *This is the service-company payoff of every confirmation.* — **Present** *(Gap #2 built — see Phase 4)*
3. **Single enforced visit state machine** (`created→scheduled→in_progress→tech_complete→closed`; cancel from created/scheduled; freeze descriptive fields after tech_complete; reject all else). — **Partial**
4. **Reversal restores stock** (extend `reverse_visit_confirmation()` to reverse `part_movements`). — **Partial**
5. **Contract entitlement** (`included_pm_visits_per_year` + per-contract-year usage counter; `contract_site` for multi-site). — **Partial** *(Gap #2: `included_pm_visits_per_year` + `count_contract_visits_in_year()` done; `contract_site` multi-site still deferred)*
6. **Customer property hierarchy** (site/building/space) + customer `type`/`billing_currency`. — **Missing**
7. **Runtime/meter triggers + BOM/where-used.** — **Missing** (lower urgency).

### ✅ Phase 2 — Gap #3 (single enforced visit state machine) — **BUILT**

Implemented end-to-end (DB → API → UI → tests), additive-only. The canonical
lifecycle **reuses the existing vocabulary** so the live data
(`scheduled`/`in_progress`/`completed`, ~2.6k rows) needs no migration:

```
created → scheduled → in_progress → completed → closed
   │          │
   └──────────┴───────────────────▶ cancelled
```

The spec's `tech_complete` is normalised onto this system's existing
`completed` state (which already locks via `submitted_at`); `closed` is the new
manager/billing terminal. Spec/colloquial aliases (`tech_complete`, `complete`,
`canceled`, `open`) are folded to canonical names on the way in.

- **Schema** (`database.py`, additive migration tuples on `maintenance_visits`):
  `closed_at`, `closed_by_kind`, `closed_by_id`, `cancelled_at`,
  `cancelled_reason`, `cancelled_by_kind`, `cancelled_by_id`. Existing rows
  untouched.
- **Service** (`database.py`): `transition_visit(visit_id, new_status, *,
  actor_kind, actor_id, reason)` — the ONE authority for status changes;
  validates against `_VISIT_LIFECYCLE`, applies canonical side-effects
  (`start_time` on in_progress; `submitted_at`+`completed_date`+`end_time` on
  completed; `closed_at`+actor on closed; `cancelled_at`+`reason`+actor on
  cancelled), returns `{old,new,noop}`, raises `VisitTransitionError` on illegal
  moves. Plus `normalize_visit_status`, `visit_transition_allowed` (pure
  predicate), and `assert_visit_edit_allowed` (freeze guard).
- **Enforcement everywhere**: `update_visit()` now runs the same guard, so the
  admin edit modal and the tech start-bump can't make an illegal jump, and a
  **completed/closed/cancelled visit's descriptive fields are frozen** (the only
  unlock is a confirmation reversal, which re-opens to `scheduled`). Encrypted
  fields are decrypted before the freeze comparison so re-saving identical
  content is allowed.
- **API** (`main.py`): `POST /api/admin/visits/{id}/transition`
  (`{status, reason}` → 409 `{scope,message,current,requested}` on illegal
  moves); `PUT /api/admin/visits/{id}` now returns **409** on an illegal status
  jump or a frozen-field edit.
- **UI** (`admin.html`): a **Lifecycle** card on the Visit Detail modal showing
  the current state + only the legal next-action buttons (Start/Complete/Close,
  and Cancel with a reason prompt); 409s surface inline.
- **Tests**: `tests/test_cmms_visit_state.py` (22 DB-level: graph shape,
  every legal move + side-effects, aliases, all illegal jumps incl. terminal
  states, `update_visit` guard, freeze + identical-resave + reversal-unlock) +
  `tests/test_cmms_visit_state_api.py` (7 HTTP: legal/illegal transition,
  cancel-with-reason, alias, 404, update illegal jump 409, frozen-edit 409).

Behavior-map delta: **Work-order state machine in ONE service fn** →
**Present** (`transition_visit`, with `update_visit` delegating to the same
guard).

### ✅ Phase 3 — Gap #4 (reversal restores stock) — **BUILT**

`reverse_visit_confirmation()` now returns the parts a visit consumed back to
inventory, **atomically** with the re-open (same connection/transaction as the
append-only reversal event), additive-only.

- **Mechanism** (`database.py`, `_restore_visit_stock`): works off the *net*
  movement per part for the visit (`SUM(part_movements.quantity_delta)` grouped
  by `part_id`, `HAVING net < 0`). Each still-out part gets a single
  compensating positive `'received'` movement of exactly `-net`, which both
  bumps `parts.quantity` and writes an auditable ledger row tagged
  *"Confirmation reversal — restored to stock (visit #…)"*. Driving the visit's
  net to 0 makes the operation **idempotent** — a second reversal (after a
  re-complete) restores nothing, and a part already returned via
  `remove_visit_part` (net 0) is left alone.
- **API/return**: `reverse_visit_confirmation(..., restore_stock=True)` (default
  on; `False` to keep parts consumed). The result dict and the event snapshot
  both carry a `restored` / `restored_stock` list of `{part_id, quantity,
  new_quantity}`. The existing `POST /api/admin/visits/{id}/reverse-confirmation`
  passes it straight through.
- **UI** (`admin.html`): the reverse-confirmation success toast now reports how
  many units across how many parts went back to stock, and the reversal-history
  rows show *"returned N unit(s) to stock"*.
- **Tests**: `tests/test_cmms_reversal_stock.py` (7: restore, idempotency
  across re-complete, partial-removal net-zero, multi-part, ledger-movement
  written, `restore_stock=False` opt-out, snapshot records restored).

Confirmation-reversal map delta: **Append-only confirmation + reversal** is now
**Present (full)** — the stock-restore caveat is resolved.

### ✅ Phase 4 — Gap #2 (billing-class layer + draft-invoice-from-confirmations) — **BUILT**

The service-company payoff: every order (visit) now resolves to ONE billing
class that decides who pays, and a draft invoice can be generated from a visit's
confirmed work with that class applied. Additive-only; live data untouched.

- **Schema** (`database.py`, additive migration tuples):
  - `maintenance_visits`: `billing_class`, `billing_class_reason`,
    `billing_class_overridden`, `billing_class_set_at`,
    `billing_class_set_by_kind`, `billing_class_set_by_id` (the cached/overridden
    decision + who/when).
  - `pm_contracts`: `included_pm_visits_per_year` (yearly entitlement; `0`/NULL =
    unlimited).
  - `create_equipment` / `create_visit` extended (additively) to persist the
    Gap #1 `warranty_months`/`status` and the `pm_contract_id` link at creation.
- **Resolution** (`database.py`, `resolve_billing_class(visit_id)`) — pure read,
  precedence highest-first:
  1. **manual override** (`billing_class_overridden=1`) — respected verbatim; the
     only path to `goodwill`.
  2. **warranty** — equipment under manufacturer warranty at the visit's service
     date (`compute_warranty_expiry()` vs. the visit's scheduled/completed date).
  3. **contract** — attached to an *active* PM contract AND within its yearly
     entitlement; past the included count → overage → `billable`.
  4. **billable** — the customer pays (default).
  Plus `set_visit_billing_class()` (stamps an override + actor),
  `count_contract_visits_in_year()` (per-contract-year window anchored on
  `start_date`; reports `{window_start, window_end, included, used, ordinal,
  exhausted}`), and `BILLING_CLASSES`.
- **Draft invoice from confirmations** (`build_draft_invoice_from_visit` /
  `generate_draft_invoice_for_visit`): aggregates the visit's labor (tracked
  hours × rate) + parts into lines, then applies the class — **billable lines
  priced normally; warranty/contract/goodwill lines documented at 0** with a
  "— covered (…)" suffix and a billing-class note on the invoice. GCT is the
  single optional `tax_rate` % line (reusing the existing invoice tax
  mechanism). Generation caches the resolved class onto the visit (never
  clobbering a manual override).
- **API** (`main.py`):
  - `GET /api/admin/visits/{id}/billing-class` — resolve (preview).
  - `POST /api/admin/visits/{id}/billing-class` — manual override
    (`{billing_class, reason}`; 422 on unknown class; audited
    `visit.billing_class`).
  - `GET /api/admin/visits/{id}/draft-invoice?tax_rate=` — preview (no write).
  - `POST /api/admin/visits/{id}/draft-invoice` — generate the draft invoice
    (audited `invoice.generate_from_visit`).
  All admin-gated via `_require_perm`/`_require_record_access`.
- **UI** (`admin.html`): a **Billing** card on the Visit Detail modal (shown once
  the visit is completed/closed) surfacing the resolved class + reason +
  contract-entitlement usage, with override buttons (Billable/Warranty/Contract/
  Goodwill, gated by `visit:update`) and a **Generate Draft Invoice** button
  (optional GCT prompt, gated by `invoice:create`).
- **Tests**: `tests/test_cmms_billing_class.py` (16 DB-level: all four classes,
  warranty-lapsed fallback, contract overage past entitlement, inactive
  contract, override-beats-warranty, unknown-class reject, draft pricing for
  billable vs. zero-for-warranty, generate with GCT, override-not-clobbered,
  entitlement window/per-year accounting) + `tests/test_cmms_billing_api.py`
  (7 HTTP: resolve, override→goodwill, 422 unknown, 404 missing, preview→generate
  with GCT totals, admin-auth required on all four routes, **portal-scoping leak
  guard** — a customer can't see another customer's invoice and drafts are hidden
  even from the owner).

Behavior-map delta: **Billing-class resolution** → **Present**;
`service_contract` and `invoice_draft / line` → **Present**.

## Recommended first build

**Gap #1 — the FL/equipment temporal split.** It's the spec's named backbone,
it's genuinely absent today, and it's self-contained (new tables + install/remove
service + invariants + a timeline view) without forking any live data. Concretely:

- `functional_location` (site/space-scoped slot, `parent_fl_id`, `fl_class`).
- `equipment_install` (equipment_id, functional_location_id, installed_at,
  removed_at NULL=active, installed_by) with two SQLite partial-unique indexes
  enforcing *one active install per FL* and *one active install per equipment*.
- Add `equipment.status` + `warranty_months` (additive migration); computed
  warranty-expiry property.
- Install/Remove endpoints + dialog that surfaces the invariant violation as a
  friendly message; equipment timeline view.
- Tests that expect `IntegrityError` on the two invariants (the Phase-1 gate).

Gap #2 (billing) is the natural follow-on and the highest *business* value, but it
leans on a clean order/confirmation spine, so #1 → #3/#4 → #2 is the suggested order.
